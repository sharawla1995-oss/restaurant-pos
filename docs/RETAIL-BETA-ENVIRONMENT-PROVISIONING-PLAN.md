# Sharawla Retail Beta Environment Provisioning Plan

Status: DESIGN / NO PROVISIONING EXECUTED
Cloud mutation: NONE
Operational DB mutation: NONE
Runtime change: NONE

This plan prepares the isolated environment required for Retail Closure acceptance after the Restaurant G0-G3 gate.

## 1. Why a dedicated Retail environment is required

Current Sharawla Cloud has:
- Retail Profile implemented=true and active=true;
- zero Businesses currently assigned to Retail Profile.

SH-0007 is already the isolated Restaurant Beta device for Business "تجريبي".

Do not repurpose SH-0007 before Restaurant acceptance is closed.

The X2 trusted operational Profile design also assumes the current operational backend is Business-scoped.

Therefore Retail acceptance should use its own:
- Cloud Business;
- Cloud Branch;
- License;
- Device;
- Business Connection;
- operational backend;
- operational Profile binding.

## 2. Recommended topology

### Sharawla Cloud

Customer:
- dedicated Beta/Test customer or existing dedicated QA customer.

Business:
- name: clear Retail Beta test name.
- pos_profile: retail.
- activity category: retail / التجارة والتجزئة.
- active: true.

Why generic Retail activity:
- activity category retail is currently active;
- specific Retail subcategories such as supermarkets, grocery, clothes, electronics, etc. currently exist but are inactive.

Do not activate a subcategory just to provision the first Retail test.

### Business Branch

Create one primary test branch first.

Recommended code:

Name:
- TEST Retail

Requirements:
- active=true;
- Cloud branch code populated from day one.

This code later maps to operational:

Do not depend on display-name matching.

### License

Dedicated Retail Beta license:
- business_id = Retail Beta Business
- branch_id = Retail test Cloud branch
- max_devices = 1 initially
- offline_grace_days = 7 unless a dedicated acceptance policy says otherwise
- active=true

Do not reuse SH-0007 license.

### Device

Dedicated physical/VM test device.

Requirements:
- new Support Code generated by Cloud;
- business_id = Retail Beta Business;
- branch_id = Retail test Cloud branch;
- license_id = Retail Beta license;
- device_classification = primary;
- architecture recorded;
- canonical fingerprint immutable after binding.

Do not preselect a Support Code in documentation.
Use the next Cloud-generated canonical Support Code.

## 3. Operational backend

Use a separate Supabase project/backend for Retail Beta acceptance.

Do not point Retail Beta to:
- Top Burger Production;
- SH-0007 Restaurant operational backend;
- Sharawla Cloud database itself.

Recommended source:
clone the accepted Beta operational schema baseline after Restaurant G0-G3 is closed.

Reason:
the current Beta schema already contains Retail tables/functions, but a new backend gives:
- trusted single Profile binding;
- clean Retail fixtures;
- no Restaurant acceptance residue;
- clear cleanup boundaries.

## 4. Schema clone gate

Before connecting the Retail Business, verify on the new backend:

- table count/schema parity as intended;
- functions present;
- RLS enabled where required;
- policies present;
- triggers present;
- extensions required by runtime;
- Retail tables/views/functions present;
- acceptance cleanup functions present;
- no Production data;
- no Production credentials.

The clone is schema-first, not data-copy of Top Burger.

Seed only Retail acceptance fixtures.

## 5. Trusted Operational Profile binding

Per X2 design, provision a private operational identity:

cloud_business_id = new Retail Beta Business UUID
profile_code = retail

Binding is provisioned from Sharawla Cloud/Admin relationship.

The POS cannot write it.

Acceptance:
- exact one trusted binding;
- Restaurant Profile assertion fails;
- Retail Profile assertion passes once X2 is implemented;
- Business ID matches the active Business Connection.

## 7. Business Connection

One active Business Connection per Business is already enforced by primary key business_id.

Connection must point only to the dedicated Retail operational backend.

Fields:
- supabase_url
- publishable key
- active=true

Validation before device activation:
- URL is expected Retail backend;
- key has publishable format;
- Business ID matches;
- RPC get_sharawla_business_connection returns Retail backend only for the Retail device.

No manual URL/key entry in POS.

- Cloud business_id is Retail Beta Business;
- profile=retail;

## 15. Cleanup / reset strategy

Acceptance fixtures need deterministic tags/run IDs.

Cleanup must:
- remove only acceptance-created entities;
- restore stock/cost;
- preserve baseline seed products/suppliers/users;
- verify residue=0.

Do not reset the whole backend after every test unless it is an explicit disposable environment operation.

## 16. Backup strategy

Before the first write acceptance:
- take schema/config checkpoint;
- ensure app backup works on Retail profile;
- record fixture seed.

After major gates:
- backup accepted state;
- keep known-good reference.

## 17. What not to do

- reuse SH-0007 Business Connection;
- connect Retail to Production;
- clone Production customer/order data;
- change Canonical Fingerprint rules;
- auto-Rebind;
- enable all Add-ons by default;
- activate Canonical Stock/Cutover as part of Retail setup;
- treat environment provisioning as product acceptance.
