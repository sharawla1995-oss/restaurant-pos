# Point 4 Batch 4B — Reservation Identity V1 Contract Design

Status: **design only**. This document is not an executable migration and does
not activate Canonical Stock. The 4B-2 committed-concurrency gate remains open.

## 1. Current source-proven contract

### Durable tables

| Object | Current identity/state | First durable role |
|---|---|---|
| `public.retail_website_orders` | `id bigserial`, unique `idempotency_key text`, unique `reservation_key text`, status, expiry, optional accepted order | Staged website-order document |
| `public.retail_website_order_items` | `id bigserial`, FK `retail_website_order_id`, product and priced quantity; unique `(retail_website_order_id, product_id)` | Aggregated product lines |
| `public.retail_stock_reservations` | `id bigserial`, branch/product/quantity, `reservation_key`, status, expiry, optional `website_order_id`; unique `(reservation_key, product_id)` | Legacy physical reservation rows |

There is no durable reservation status-history/mutation table. Status changes
update the order and reservation rows in place.

### Functions and callers

| Command | Current function | Caller | First durable write | Existing retry identity |
|---|---|---|---|---|
| Create | `public.retail_create_website_order(bigint,text,text,text,text,text,bigint,text,text,text,text,jsonb)` | `retail-website/app.js::submitOrder()` | Insert `retail_website_orders`, then items and reservations in one transaction | Browser-generated `p_idempotency_key`; wrapper locks and replays by that key, but does not compare a complete economic digest |
| Legacy reserve | `public.retail_reserve_stock(bigint,text,jsonb,integer)` | No current public website caller; anon/authenticated EXECUTE is revoked by beta18 finalize | Upsert `retail_stock_reservations` | `reservation_key`; rows aggregate by product |
| Accept | `public.accept_retail_website_order(bigint)` | `retail-website-pos.js` | Creates POS order, consumes reservation, updates staged order | Lock/replay by generated website-order DB ID; no mutation TX |
| Reject | `public.reject_retail_website_order(bigint,text)` | `retail-website-pos.js` | Updates staged order and releases reservation | Status-only replay; no mutation TX/digest |
| Customer cancel | `public.cancel_retail_website_order_customer(text,text)` | `retail-website/app.js` | Updates staged order and releases reservation | No mutation TX/digest |
| Expiry | Inline updates in reservation/create/accept paths | Server functions | Updates reservation/order where the surrounding transaction commits | No durable expiry-command identity |

The website is online RPC based; this flow does not use Native Offline V2,
SQLite, Outbox, Sync, or Offline ACK ownership. The browser currently generates
new `idempotency_key` and `reservation_key` values for each submit invocation;
it does not persist a pending command before the call, so a retry after an
ambiguous response is not guaranteed to reuse them.

The create implementation groups input by `product_id`. Therefore duplicate
product entries are deliberately collapsed today. Neither generated order/item
IDs nor `reservation_key` can be reclassified as Identity V1 `document_uid` or
`line_uid`.

## 2. Exact gaps

1. No immutable lowercase UUIDv4 `document_uid` exists before the first write.
2. No immutable UUIDv4 `line_uid` exists for a genuine submitted line.
3. Duplicate products cannot retain distinct identities in the Legacy item or
   reservation tables because both models aggregate by product.
4. `idempotency_key` is not the approved typed creation `client_tx_id`, and
   replay does not verify a canonical operation digest.
5. Accept/reject/cancel/expiry have no durable mutation identity or digest.
6. Current generated DB IDs are lookup/lineage only and are unavailable before
   creation.
7. Adding optional parameters to existing functions risks positional-call
   ambiguity and still cannot store distinct canonical lines safely.

## 3. Proposed additive schema contract

All new objects remain inactive until a separately reviewed executable
migration and runtime adapter are approved.

### `public.retail_reservation_documents_identity_v1`

| Column | Type / nullability | Contract |
|---|---|---|
| `id` | `bigint generated by default as identity primary key` | Internal lineage only |
| `retail_website_order_id` | `bigint not null unique` | FK to `retail_website_orders(id)` with `ON DELETE RESTRICT` |
| `document_uid` | `uuid not null unique` | Immutable canonical reservation document identity |
| `creation_client_tx_id` | `uuid not null unique` | Immutable creation mutation identity; not the document identity |
| `creation_operation_digest` | `bytea not null` | SHA-256 of canonical creation intent |
| `identity_contract_version` | `text not null` | Check exactly `sharawla.point4.identity.v1` |
| `created_at` | `timestamptz not null default now()` | Audit only; excluded from economic digest |

`source_document_id` is derived as `uuid:` plus lowercase `document_uid`; it is
not independently mutable storage. UUID input must satisfy the Identity V1
lowercase UUIDv4 textual validation at the RPC boundary before casting.

### `public.retail_reservation_lines_identity_v1`

| Column | Type / nullability | Contract |
|---|---|---|
| `id` | `bigint generated by default as identity primary key` | Internal lineage only |
| `reservation_document_id` | `bigint not null` | FK to identity document with `ON DELETE RESTRICT` |
| `line_uid` | `uuid not null unique` | Immutable identity for one genuine submitted line |
| `product_id` | `bigint not null` | FK to `products(id)` with `ON DELETE RESTRICT` |
| `quantity` | `numeric(14,3) not null` | Positive, losslessly normalized quantity evidence |
| `reservation_effect_line_key` | `text not null unique` | Identity V1 deterministic, non-nested reservation effect key |
| `canonical_line_digest` | `bytea not null` | Canonical line intent digest |
| `created_at` | `timestamptz not null default now()` | Audit only |

Unique `line_uid` and effect key preserve two lines containing the same product.
The existing aggregated order-item and stock-reservation rows remain the Legacy
operational projection. A future versioned create RPC may aggregate canonical
lines for those Legacy projections while persisting every genuine canonical
line in this sidecar in the same transaction. It must verify that per-product
aggregates exactly equal the sidecar totals; it must not silently merge the
canonical identities.

### `public.retail_reservation_mutations_identity_v1`

| Column | Type / nullability | Contract |
|---|---|---|
| `id` | `bigint generated by default as identity primary key` | Internal lineage only |
| `reservation_document_id` | `bigint not null` | FK to canonical reservation document, `ON DELETE RESTRICT` |
| `client_tx_id` | `uuid not null unique` | One immutable logical status mutation |
| `mutation_type` | `text not null` | Check: `accept`, `reject`, `cancel`, `expire` |
| `operation_digest` | `bytea not null` | Canonical mutation intent digest |
| `requested_status` | `text not null` | Check matching the mutation contract |
| `result_status` | `text null` | Durable authoritative result after application |
| `result_payload` | `jsonb null` | Stable replay result; generated IDs are lineage, not identity |
| `actor_employee_id` | `bigint null` | FK to employees for staff mutations; null for customer/system |
| `recorded_at` | `timestamptz not null default now()` | Audit only, excluded from digest |
| `applied_at` | `timestamptz null` | Result timestamp, excluded from digest |

Creation identity is stored on the document; status changes are append-only
mutation rows. `document_uid` is lineage and must never be used as the mutation
idempotency key. Mutation rows and canonical identity columns require BEFORE
UPDATE/DELETE immutability triggers. Result fields may be filled exactly once by
the owning versioned RPC; identity, type, digest, lineage, and applied result
must thereafter be immutable.

### Partial-envelope and lifecycle enforcement

The sidecar design makes canonical membership explicit: a Legacy order has no
identity-document row; a Canonical reservation has one complete NOT NULL row
and at least one complete canonical line. This avoids nullable partial identity
columns on Legacy tables. The versioned creation function must insert order,
identity document, all identity lines, aggregated Legacy projections and stock
reservations atomically, then verify line/aggregate equality.

Deferred constraints requiring triggers rather than plain CHECKs:

- prevent changing/deleting document, line and mutation identities;
- require at least one canonical line before creation returns;
- require all canonical lines to belong to the same resolved document;
- enforce mutation type → requested status mapping;
- prevent a second distinct successful terminal mutation once state no longer
  allows it, while permitting exact replay of the original TX;
- ensure no sidecar can be attached later to a pre-existing Legacy order.

## 4. RPC compatibility contract

Recommended architecture: **new versioned RPCs**, leaving every deployed
signature and existing caller unchanged.

1. `retail_create_website_order_identity_v1(p_request jsonb) returns jsonb`
   accepts a strict allowlisted request containing `client_tx_id`,
   `document_uid`, canonical `source_document_id`, and lines with `line_uid`.
   Unknown identity/economic fields fail closed. The function validates and
   persists the complete envelope before returning and performs all Legacy
   operational projection writes in the same transaction.
2. `accept_retail_website_order_identity_v1(p_document_uid uuid,
   p_client_tx_id uuid, p_operation_digest text) returns jsonb`.
3. `reject_retail_website_order_identity_v1(p_document_uid uuid,
   p_client_tx_id uuid, p_operation_digest text, p_reason text) returns jsonb`.
4. `cancel_retail_website_order_customer_identity_v1(p_document_uid uuid,
   p_client_tx_id uuid, p_operation_digest text, p_customer_phone text)
   returns jsonb`.
5. `expire_retail_website_order_identity_v1(p_document_uid uuid,
   p_client_tx_id uuid, p_operation_digest text) returns jsonb`, invoked by an
   approved online system owner. That owner generates and durably retains the
   UUIDv4 command identity before calling; the database must not generate a new
   TX during retry.

Passing a generated website-order ID may be supported as an additional lookup
cross-check, never as canonical identity or digest input. Existing RPCs remain
Legacy and keep their existing grants and behavior until separately cut over.
Overloading an existing function or appending default parameters is rejected:
PostgREST and positional callers can resolve overloads/defaults ambiguously,
and such a change would obscure the Legacy-versus-Canonical boundary.

## 5. Database-enforceable idempotency

For every versioned mutation:

1. Validate UUID/document/line envelope and build the canonical digest.
2. Acquire `pg_advisory_xact_lock` on a domain-separated hash of
   `client_tx_id`.
3. Look up the durable document or mutation row by `client_tx_id`.
4. Same TX + byte-identical digest returns the stored authoritative result.
5. Same TX + different digest raises an explicit idempotency conflict.
6. A new TX locks the reservation document/current order row, validates the
   state transition, appends the mutation row, applies the existing Legacy
   state/reservation effect once, stores the result, and commits atomically.

Creation additionally locks both `creation_client_tx_id` and `document_uid`.
Reusing either with inconsistent payload fails closed. Different logical
mutations require different TX values. Retrying the same mutation must retain
the original TX outside the database; the server never substitutes one.

## 6. Legacy compatibility matrix

| Caller/data | Behavior |
|---|---|
| Existing website create caller | Continues calling the current RPC unchanged; creates Legacy rows only |
| Existing accept/reject/cancel callers | Continue unchanged with current Legacy state behavior |
| Existing reservation/order rows | No sidecar, remain explicitly Legacy |
| Reads of historical rows | Never generate UUIDs and never attach sidecars |
| New Identity V1 caller | Calls only versioned RPCs and must supply the complete envelope |
| Partial/malformed Identity V1 | Versioned RPC fails closed before any durable write |
| Canonical caller invoking Legacy RPC | Runtime adapter must prohibit this after future activation; not implemented here |

## 7. Required constraints, indexes and security

- Unique indexes: document UID, creation TX, line UID, effect line key, mutation
  TX, and one sidecar per website order.
- Lookup indexes: document FK, line document FK/product, mutation document/time.
- FK delete behavior is `RESTRICT`; no canonical audit lineage cascades away.
- RLS enabled on all three public sidecar tables. No direct INSERT/UPDATE/DELETE
  grant to `anon` or `authenticated`; narrowly scoped staff SELECT policies may
  follow the parent branch-access rule. Customer reads remain RPC-only.
- Versioned mutators, if `SECURITY DEFINER`, use `SET search_path=''`, fully
  qualified references, explicit auth/branch checks, and explicit
  `REVOKE EXECUTE FROM PUBLIC, anon, authenticated` followed only by the exact
  required grants. The customer create/cancel surfaces require the same
  anti-abuse and phone-ownership checks as the current API.
- Internal helpers are not executable by clients.

## 9. Exact future SQL object impact

Create:

- tables `retail_reservation_documents_identity_v1`,
  `retail_reservation_lines_identity_v1`,
  `retail_reservation_mutations_identity_v1`;
- their PK/FK/check/unique constraints and lookup indexes;
- identity/result immutability trigger functions and triggers;
- five versioned RPCs listed above plus private validation/idempotency helpers.

Reference without altering ownership semantics:

- `retail_website_orders`, `retail_website_order_items`,
  `retail_stock_reservations`, `branches`, `products`, `employees`, `orders`,
  and the current Legacy functions/core where reuse is proven safe.

No Point 4B-1/4B-2 object, Canonical Stock balance/movement, Offline object, or
current RPC signature is changed by this design.

## 10. Risks and open decisions

1. **Client durable retry owner:** the retail website currently lacks a durable
   pending-command/outbox owner. Architecture approval is needed for a minimal
   browser pending-command record or an online gateway owner; it must not create
   a second Offline V2 owner.
2. **Duplicate-product presentation:** canonical sidecar lines preserve genuine
   lines, while the current operational projection aggregates products. UI and
   pricing rules must confirm whether separate notes/discounts on duplicate
   product lines are valid; the contract must never silently discard them.
3. **Expiry owner:** choose the single scheduler/request owner that durably owns
   expiry TX values. Lazy expiry inside a transaction that later raises cannot
   be treated as durable mutation evidence.
4. **Digest specification:** exact strict allowlists for creation and each status
   mutation must be approved using Identity V1 helpers before implementation.
5. **Public security/rate limiting:** versioned anonymous create/cancel requires
   abuse controls equivalent to or stronger than the current RPC.

None of these decisions authorizes Canonical Stock routing or changes the open
4B-2 concurrency gate.

## 11. Proposed implementation sequence

1. Approve this sidecar + versioned-RPC design and resolve the client retry and
   expiry ownership decisions.
2. Implement an additive migration source only; run static/security review.
3. Run a read-only deployment preflight on isolated Beta.
4. Apply only after explicit approval, then validate schema/security contracts.
5. Add website/POS identity generation and durable retry propagation while
   leaving Legacy stock ownership active.
6. Run reservation Identity V1 database/runtime acceptance.
7. Only after 4B-2 committed concurrency closes, separately review Batch 4B
   routing into the inactive Canonical adapter and eventual controlled cutover.
