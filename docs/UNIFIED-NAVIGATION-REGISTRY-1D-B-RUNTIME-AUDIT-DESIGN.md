# Unified Navigation Registry — Batch 1D-B Runtime Shadow Audit Design

Status: DESIGN / REVIEW ONLY — NOT RUNTIME-BOUND  
Baseline: `2dfc07a2e41ed6a73151268d6b6d2889777c0f82`  
Target runtime: SH-0007 only  
Production: SH-0005 / SH-0006 are out of scope and must remain untouched.

## Purpose

1D-B verifies that the runtime route actually rendered by Sharawla matches the owner, renderer, augmentation, profile, permission, feature, and location expectations already proven statically by 1C and classified by the pure 1D-A auditor.

A page merely becoming visible is not owner evidence.

The runtime collector must produce attributable evidence for the renderer/owner that actually produced the visible page. If attributable evidence cannot be produced, the result is an evidence gap / mismatch and never a canonical match.

## Hard boundary

The 1D-B probe is observation-only.

It must not:

- call `showPage()`;
- invoke any renderer;
- call `.click()`;
- call `preventDefault()`, `stopPropagation()`, or `stopImmediatePropagation()`;
- add click/key/navigation event handlers;
- wrap or replace runtime functions;
- monkey-patch DOM APIs;
- write localStorage/sessionStorage/IndexedDB;
- call REST/RPC/fetch/XHR;
- mutate permissions, feature flags, location scope, runtime config, or business data;
- mutate navigation or page DOM;
- select a canonical owner for a conflict;
- convert Deferred / Conflict / New Target into canonical success.

The probe must not use `beta55-navigation-parity.js` routing/sync methods as its transport. That layer contains active routing and DOM synchronization behavior.

## SH-0007 sandbox lock

The probe must refuse to start unless all available lock evidence identifies the isolated Beta sandbox:

- support code = `SH-0007`;
- update channel/version is Beta;
- business = the existing isolated Beta business;
- backend host = the existing isolated Beta backend.

A lock mismatch is a hard FAIL/NO-START. No fallback to another device or backend.

The probe must not read, log, or export canonical fingerprint values, license keys, publishable keys, auth tokens, or credentials.

## Instrumentation choice

### Rejected approaches

1. **Click listener / capture listener instrumentation**
   Rejected because listener ordering can interact with Restaurant Closure, Beta54, Central Warehouse, and Navigation Parity.

2. **Wrapping `showPage` or renderer functions**
   Rejected because it changes the execution path and can create false ownership evidence.

3. **MutationObserver as the primary trigger**
   Rejected for the first runtime gate because observer callback ordering would be introduced into a runtime that already contains multiple MutationObservers.

4. **DOM setter/prototype monkey-patching**
   Rejected because it is intrusive and can alter behavior.

5. **Navigation Parity `route()` / `syncHomeCards()`**
   Rejected because those methods can click buttons and mutate Home/navigation DOM.

### Selected mechanism: post-render read-only sampler

Use a low-frequency, read-only sampler that only reads current runtime state after existing handlers/renderers have completed.

The sampler:

- starts only after required runtime owner globals are present;
- does not subscribe to click or navigation events;
- does not install a MutationObserver;
- samples at a conservative interval;
- records a new observation only when the normalized visible-route fingerprint changes;
- keeps observations in memory and/or console output only for the initial gate;
- stops automatically after the acceptance window.

The sampler is diagnostic infrastructure, not a router.

## Actual owner evidence model

Each canonical-capable route must have a **source-bound runtime signature**.

A signature is accepted only when a static checker proves all of the following:

1. the signature literal/selector is produced by the declared renderer owner source;
2. it is unique enough in the runtime source graph to attribute the rendered page to that owner;
3. the runtime DOM currently exposes that signature;
4. the active route/navigation state is consistent with the route;
5. the expected renderer name and owner are carried into the 1D-A audit input;
6. an evidence record identifies the signature and source owner.

Example evidence object:

```text
routeKey
rendererOwner
renderer
navigationOwner
augmentationLayers[]
sourceEvidence[]
runtimeSignatureId
observedAt
```

Opening the correct-looking page without a source-bound signature is not sufficient.

## Existing strong signature candidates

These are candidates for the implementation contract and must still pass static uniqueness checks before use:

- `orders`: `[data-orders-runtime="ORDERS-DATE-WINDOW-V58.3"]` from `app.js`.
- Beta54 HR/Treasury routes: Beta54-specific active navigation plus Beta54 page structures/classes generated by `beta54-shared-core-ui.js`.
- Restaurant Closure routes: route-specific visible content/structures generated by `beta55-restaurant-closure-ui.js`.
- `internalSupply`: `b55s-*` structures plus `[data-beta55-supply-page].active` generated by `beta55-central-warehouse-ui.js`.
- `users`: base Users page signature from `app.js`; Permissions V2 augmentation is separate evidence and must not be mistaken for renderer ownership.

For ordinary `app.js` routes, each route needs an individually proven unique composite signature. Generic `.panel` or page title alone is not owner evidence.

If a route does not have a sufficiently unique source-bound signature, it remains `EVIDENCE_GAP` / mismatch for 1D-B until evidence is added by a separately reviewed additive mechanism.

## Route-state discovery

The sampler may read, but must not modify:

- active `button[data-page]`;
- active `button[data-beta54-page]`;
- active `[data-beta55-supply-page]`;
- `#pageTitle`;
- `#page` descendants required by the signature contract;
- visibility state of known registered navigation controls.

`group:hr` remains a Group, not a Route.

`manageBranchesBtn`, `addBranchBtn`, `changeBranchBtn`, and `logoutMenuBtn` remain Actions, not Routes.

Website Hub children are evaluated as hub-child routes and must retain their current navigation-owner classification.

## Classification rules

Runtime observations feed the already-pure 1D-A auditor.

- ordinary route with attributable matching owner evidence -> `SHADOW_MATCH`;
- Orders V58.3 with attributable matching evidence -> `SHADOW_LOCKED_MATCH`;
- `suppliers`, `purchasing`, `stockCount`, `transfers` -> always `SHADOW_CONFLICT_BLOCKED`;
- `websitePayments` and other registered deferred routes -> `SHADOW_DEFERRED`;
- `summary` -> `SHADOW_NEW_TARGET`;
- unknown or insufficient evidence -> never canonical; report `UNKNOWN`, `SHADOW_MISMATCH`, or explicit evidence gap.

A currently executing owner on a conflict route is runtime evidence only. It must never become canonical ownership in 1D-B.

## Visibility checks

The runtime sampler must compare actual visibility with the expected profile/feature/permission/location context without changing that context.

Minimum negative checks:

- Retail-only route visible in Restaurant -> FAIL.
- Disabled feature route visible -> FAIL.
- Route visible without required permission -> FAIL.
- Location-scoped route exposed outside allowed location -> FAIL when a concrete location expectation is available.

The probe must not change user, role, feature, branch, or location merely to manufacture a negative case. Scenario changes belong to a separately controlled acceptance plan.

## Augmentation evidence

Augmentation is recorded separately from renderer ownership.

Examples:

- `users`: `permissions-v2-ui.js` may provide augmentation evidence, while `app.js` remains renderer owner.
- `internalSupply`: `beta55-central-warehouse-v2.js` augmentation must remain separate from `beta55-central-warehouse-ui.js` renderer/navigation ownership.
- Purchasing augmentation layers do not resolve the Purchasing conflict.

Missing required augmentation evidence causes mismatch/evidence gap; it must not silently change the renderer owner.

## Runtime lifecycle

1. Verify exact SH-0007 sandbox lock.
2. Wait read-only for required owner globals to be present.
3. Start low-frequency sampler.
4. Observe operator-driven navigation only; never initiate navigation.
5. On visible-route fingerprint change, collect runtime signatures.
6. Build attributable actual evidence.
7. Feed evidence to 1D-A classification logic.
8. Emit in-memory/console audit record.
9. Stop after the bounded test window.
10. Produce a copied/manual report without DB or storage writes.

## Acceptance set for first SH-0007 pass

The operator navigates normally to the routes under test. The probe must not navigate on their behalf.

Required representative coverage:

- Core/app owner: `customers`.
- Locked owner: `orders`.
- Restaurant Closure: at least `tables`, `foodIngredients`, `foodRecipes`, `foodOperations`.
- Beta54: `employees`, `advances`, `adjustments`, `payroll`, `treasury`.
- Central Warehouse: `internalSupply` when enabled/allowed.
- Website Hub child: at least one normal child.
- Deferred: `websitePayments` remains deferred.
- Conflict: `purchasing` remains conflict-blocked regardless of observed active owner.
- Profile leakage: `marketSettings` and `retailOffers` must not be visible in Restaurant.
- Group/action classification remains intact.

Additional routes can be added once their source-bound signatures are statically proven.

## 1D-B pre-bind static gate

Before the runtime probe is added to the runtime graph, a static checker must prove:

- SH-0007 hard lock exists and has no fallback;
- no forbidden event-control/navigation-control APIs;
- no renderer invocation/wrapping;
- no DOM mutation APIs;
- no storage or network writes;
- no secret/fingerprint logging;
- every configured runtime signature maps to a registered route;
- every canonical-capable signature is source-bound to the expected owner;
- signature uniqueness/confidence passes the declared threshold;
- conflict/deferred/new-target classifications are immutable;
- Orders V58.3 owner/signature is unchanged.

Only after this gate passes may a separate runtime-binding change be reviewed.

## Runtime binding placement

If implementation is approved later, the preferred binding is a dedicated diagnostics script loaded last in a special Beta test build, with its own SH-0007 hard lock.

It must not be inserted into existing capture/bubble navigation handlers and must not be wired through Navigation Parity.

Because `beta36-integration-loader.js` loads important owners dynamically, the probe must not assume that static `index.html` order means all owners are ready. It should poll read-only for required readiness globals rather than registering another navigation/integration event listener.

The first binding is Beta-only and SH-0007-only. There is no Stable/Production propagation in 1D-B.

## Rollback

1D-B is additive diagnostics only.

Rollback removes the dedicated probe binding/script. Existing owners, renderers, navigation handlers, permissions, Offline/Sync, Orders V58.3, printing, updater, licensing, Business Connection, fingerprint, Point 4, and stock ownership remain unchanged.
